Execution And Hot-Path Map

Ranked Optimization Findings

1. Queue buckets are recomputed many times per render

Nano Banana Helper/Services/BatchOrchestrator.swift:86-107; Nano Banana Helper/Views/ProgressQueueView.swift:142-231,405-414
High

Current patternEach computed bucket flattens activeBatches and filters tasks. The queue view asks for pending, processing, completed, cancelled, and failed lists several times while rendering and while building the refresh identity.

Current complexityO(k * n) per body pass where n is active tasks and k is the number of bucket reads. Swipe actions add another lookup before removal.

Recommended changeBuild a queue snapshot once per render or in the orchestrator: all tasks, buckets, counts, and refresh key. Pass the snapshot through the view instead of calling computed arrays repeatedly.

AfterO(n) per snapshot pass. Risk is medium because list identity, deletion offsets, and the existing .id(queueContentRefreshID) behavior must stay equivalent.

2. OpenAI batch result application does repeated task lookup

Nano Banana Helper/Services/BatchOrchestrator.swift:910-978
High

Current patternFor each success and failure, the code searches batch.tasks.first(where: remoteRequestId == customID).

Current complexityO((s + f) * n) for result application. This is most visible on provider-side Batch Tier runs with many request lines.

Recommended changeBuild [String: ImageTask] once from non-terminal tasks keyed by remoteRequestId, then look up each success/failure in O(1).

AfterO(n + s + f). Risk is medium: must preserve duplicate custom-id handling, terminal-task guard, and existing tests around duplicate side effects.

3. Queue removal methods scan batches for every removed task

Nano Banana Helper/Services/BatchOrchestrator.swift:560-610
Medium

Current patternEach clear/remove path maps offsets through a computed bucket, then searches activeBatches and each batch task list for every selected task.

Current complexityO(r * b * t) plus the computed bucket scan, where r is removed tasks, b is batches, and t is average tasks per batch.

Recommended changeConvert selected task IDs to a Set<UUID>, then walk each batch once and remove matching tasks. Share a single helper across failed/cancelled/completed/pending removals.

AfterO(n + r). Risk is low-medium; deletion offset semantics and empty-batch cleanup need focused tests.

4. Usage snapshots do several full passes over the same ledger slice

Nano Banana Helper/Views/UsageSupport.swift:80-143,185-255; UsageDashboardView.swift:13-18
Medium

Current patternmakeSnapshot filters, sorts, then separately reduces totals, filters chart entries, groups project/model/resolution breakdowns, and computes recent activity.

Current complexityO(n log n + n * passes + d) per snapshot build. It is recomputed through a view computed property whenever SwiftUI evaluates the dashboard/report body.

Recommended changeKeep correctness first: either memoize the snapshot by ledger identity/filter or fold totals and grouped aggregates into one pass after filtering. Preserve chart exclusion rules for adjustments and legacy imports.

AfterO(n log n) if sort remains, with lower constant cost. Risk is medium because usage/accounting tests encode important edge cases.

5. History and results row rendering does per-row project lookup

Nano Banana Helper/Views/HistoryView.swift:45-59,111-124; ResultsView.swift:14-18,72-97; ProjectGalleryView.swift:25-29
Medium

Current patternFor every visible history/result entry, the view searches projects.first(where: id).

Current complexityO(entries * projects) in row/card construction. Usually acceptable, but it grows with long history and many projects.

Recommended changeBuild [UUID: Project] once in the view or manager and use direct lookups. Keep deleted-project fallback behavior.

AfterO(entries + projects). Risk is low if fallback labels remain unchanged.

6. Staging duplicate detection is linear per added file

Nano Banana Helper/Models/BatchStagingManager.swift:134-142
Low

Current patternNew URLs are filtered with !stagedFiles.contains(url).

Current complexityO(newFiles * stagedFiles), visible only when dragging large directories or many images into an already large staging list.

Recommended changeUse a temporary Set<URL> or maintain a staged URL set if duplicates are checked frequently.

AfterO(newFiles + stagedFiles). Risk is low; preserve insertion order for newly accepted files.

False Positives And Watch Areas

Pricing and model catalog are mostly constant-size

AppPricing.swift and ModelCatalog.swift dominate scanner output after the orchestrator, but the underlying model/profile arrays are tiny. Do not optimize these first unless the catalog becomes dynamic or large.

AppPaths work is not a normal hot loop

The migration and bookmark-refresh code is I/O-bound and happens around storage setup or reauthorization. Its complexity matters less than preserving sandbox correctness.

Keep log-size pressure in mind

Prior hardening already caps request/response logs. Continue treating raw base64 payload logging as a performance and memory risk even when algorithmic complexity is not the issue.

Provider API loops are dominated by network and file I/O

NanoBananaService has loops for JSONL lines, multipart fields, image uploads, and response candidates. Most are linear and appropriate; batching/deduping is already visible in OpenAI file uploads by path.
